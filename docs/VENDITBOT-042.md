# VenditBot 0.4.2 candidate

The sidebar app-connection control is larger, and a bug button opens a durable report form. Reports keep their exact request identity across uncertain responses and display their persisted state through the 리포트 agent. An enabled Rabbit connection can discover the exact VenditBot repository without requiring a local checkout. A 202 receipt is only acceptance; database/runner readiness failures and missing merge evidence remain visible. Local autonomous development is unavailable unless a real development executor is installed. The report UI does not create GitHub write permission or turn a normal chat into a test/merge executor.

Agent and team selection focuses the composer. Assistant turns show the agent name, user turns omit the redundant 나 label, and the compact composer places 입력 on the right. Images and UTF-8 text files can be selected with + or dropped into the conversation. Files are privately staged, validated and passed to supported provider inputs; switching conversations or receiving a delayed result keeps attachments on the correct draft. Supported limits are five files, 12 MiB total, 4 MiB per image and 256 KiB per text file. PDF/Office input is explicitly unsupported in this release.

`apps/ios` contains the read-only SwiftUI prototype and a detailed I01–I09 development plan. Standalone core checks do not constitute an iOS build or actual device installation. Remote command submission, durable drafts, team sync and device testing remain follow-up work.

App connection errors now distinguish macOS secure-storage waiting, timeout, failure and unavailability. Reading a private registration has its own visible stage. Messages use fixed local error codes; native error details are never copied to the screen. Existing encrypted data, cancellation and late-result guards are unchanged.

Production packaging requires the explicitly pinned existing signing certificate. Every copied native binary, framework, helper and main app is signed with that certificate. The designated requirement binds each component's own identifier to the certificate, and the extracted ZIP is verified again. Routine releases must match the previous certificate-signed app; the first transition from ad-hoc signing is explicit. Ad-hoc packaging remains available only with `--development`.

The synthetic native continuity test passed on macOS with two genuinely different Electron 42.11.12 bundles signed by the pinned certificate: encrypt on version 1.0.0, replace the bundle at the same path, and decrypt the unchanged ciphertext on 1.0.1. The driver checks both the suffixed and legacy UUID accounts are absent before launch, then removes only its proven-new synthetic item. Electron's downstream non-MAS patch uses the account suffix ` Key`; the initial diagnostic omitted that suffix and is retained as a failed test. Observing the expected pair does not audit all native item access. This synthetic result does not by itself prove that the installed application's existing ad-hoc credential grant has migrated. No Keychain search-list, ACL or existing credential change is part of the driver.

The currently installed 0.4.1 Keychain access issue remains unresolved until the stable identity and any initial OS approval are complete. Changing signing policy does not silently authorize an existing credential. See [personal signing](personal-signing.md) for operator commands and release gates.
